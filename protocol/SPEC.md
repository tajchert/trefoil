# Trefoil direct T3 wire contract

Pinned reference: T3 Code `46449b5379a0089f4ef3ce85bce10a1d28beb4cb`.
Sources: `packages/contracts/src/{environment,environmentHttp,auth,orchestrationV2,server,providerPolicy,modelSelection}.ts`, `packages/shared/src/remote.ts`, `apps/server/src/ws.ts`, installed Effect 4.1.2 `src/rpc/{RpcMessage,RpcSerialization}.ts`.

1. Parse a direct pairing URL's fragment/query `token` (or `t3code:` wrapper `pairingUrl`). HTTPS is the default. Literal RFC1918 private IPv4 HTTP origins require explicit per-environment `allowInsecureHttp` consent; public HTTP and private-looking DNS hosts are rejected. Explicit loopback development URLs may use HTTP (`localhost`, `127.0.0.1`, `::1`); the emulator host address `10.0.2.2` requires the private-LAN consent like other RFC1918 addresses. No redirects are followed; bootstrap and bearer credentials cannot cross origins.
2. GET `/.well-known/t3/environment`, require `orchestrationProtocolVersion: 2`, retain `environmentId`.
3. POST form `/oauth/token`: `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `subject_token=<bootstrap>`, `subject_token_type=urn:t3:params:oauth:token-type:environment-bootstrap`, `requested_token_type=urn:ietf:params:oauth:token-type:access_token`, mobile client metadata. Save only issued Bearer access token.
4. Each connect checks descriptor identity and authenticated `/api/auth/session` using bearer. Effective permissions (falling back to legacy scopes only when absent) control `orchestration:operate` writes.
   A machine may have several routes (LAN, Tailnet, public HTTPS, SSH, T3 Connect tunnel); the bearer belongs to the host and is valid on each. Connect walks them in order: each passes the URL policy and answers the credential-free descriptor as the saved `environmentId` within 3 s (LAN/Tailnet) or 15 s (public/tunnel) before the bearer is sent; a 401/403 or unauthenticated session stops the walk. The first config comes from `subscribeServerConfig` with T3 mobile's opt-ins `{workspaceSnapshotsOnDemand, providerCatalogsOnDemand, providerCatalogDigests, providerStatusDeltas}` (all `true`; never `omitProviders`; older servers drop unknown keys and send the full shape): its first `{version:1,type:"snapshot",config}` replaces `server.getConfig`, like T3 client-runtime (#35072), and carries the same environment (shell-resume origin), settings, capabilities, providers with models, usage limits and runtime modes, and `directEndpoints` (hints only, re-verified before use; possibly partial while the server defers network discovery, so the first route hint from a snapshot only adds learned routes; a later snapshot that changes the list, or 10 s after that hint with none, gives the complete list that may also remove them; `server.getConfig` lists are complete). Providers then lack per-cwd `workspaceSnapshots` and carry a `catalogDigest` instead of slash commands and skills, none of which Trefoil reads. Only when the server rejects or ends that stream before its first snapshot does the client fall back to `server.getConfig` `{}`; a stream that is silent past the request timeout fails the connect like a timed-out request. Events that arrive before the first config is published are applied on top of it in order. The client also reads `GET /api/connect/link-state` with bearer (5 s, failures ignored; `tunnelHostname` is newer than this pin and optional, as are `managedTunnelActive` and `linkRevoked`). Later stream events update the client: a `snapshot` (providers, settings, policy, `directEndpoints`), `settingsUpdated`, `providerStatuses` (the whole provider list) and `providerStatusDeltas` (every provider in order; `models`, `slashCommands` or `skills` left out when unchanged are taken from the held provider with that `instanceId`, T3 `applyServerProviderDeltas`; one with no `models` to restore is dropped) keep the model catalog, provider instances and usage limits current; other event types are ignored. The stream's end after the first config never fails the session.
5. POST `/api/auth/websocket-ticket/rpc` with bearer, falling back to `/api/auth/websocket-ticket` **only for HTTP 404**. Upgrade `/ws?wsTicket=<ticket>&orchestrationProtocol=2`. Do not send bearer in the WebSocket URL.
6. Effect JSON Request: `{ "_tag":"Request", "id":"1", "tag":"orchestration.subscribeShell", "payload":{"requestCompletionMarker":true}, "headers":[] }`. This is not JSON-RPC 2.0. JSON object or array frames are accepted. Chunk values receive Ack keyed by `requestId`; terminal Exit carries Success/value or Failure/cause. Cancel streams with Interrupt. Ping every 15 seconds, expire missing Pong after 45 seconds.
7. Request full shell and thread snapshots without optional compact/bounded/deduped encodings. Shell updates merge by ID and remove explicitly. Selected-thread snapshots project messages, runs, activity and pending runtime requests. Domain events invalidate writes and trigger a conflated authoritative `getThreadProjection` read (at most one in-flight and one queued refresh). Subscription completion markers gate writes. Reconnect discards old subscriptions and reads fresh state; old generations cannot apply callbacks.
8. Mutations carry a `commandId` and are sent once; a timeout, disconnect, invalid result (a `dispatchCommand` success whose value is not an object with a non-negative integer `sequence`) or an Exit whose cause only reports `Interrupt` is an uncertain outcome that fails the session (writes disabled) and is reconciled from server state, never replayed. Any other failed Exit (a typed `Fail`, e.g. `OrchestrationV2DispatchCommandError`/`OrchestrationV2ThreadLaunchError`, or a `Die` payload-decode defect) is a definite rejection: the session stays connected and the user sees "T3 rejected the <subject>". Effect encodes the cause as an array of reasons; a single reason object is tolerated. `message.dispatch` has a UUID `commandId` and `messageId`, text, empty attachments, and `dispatchMode.type` `queue_after_active` while the selected thread has an active run or its run/shell status is `preparing`/`starting` (like T3 mobile; the server queues behind an active run either way), else `start_immediately`; it also carries the required creation provenance `createdBy: "user"` and `creationSource: "mobile"` (T3 `OrchestrationV2CreationFields`; without them the server rejects the payload). A follow-up while the thread works is either queued (`queue_after_active`, no intent) or steered (`start_immediately` with top-level `deliveryIntent: "steer"`); steer is refused locally unless the active turn can steer (T3 `canPromoteToSteer`: the provider session's `capabilities.turns.supportsActiveSteering`/`supportsSteeringByInterruptRestart`, a setup-phase run with no known session, or an active `/compact`; blocked while compaction runs unless `activeSteeringDuringCompaction`), and an idle thread starts immediately either way. Queued user messages are the projection's `queued` runs without `delegatedCompletion`/`notification` wakes, ordered by `queuePosition ?? ordinal` then `ordinal`, with text from `messages` by `userMessageId` (fallback "Queued message"); the queue is held when any queued run has `queueHeld`. Queue commands: `queued-run.cancel {runId}`, send-now as `queued-message.promote-to-steer {queuedRunId, targetRunId}` into the active run or `queued-run.start {runId}` when no run is active, and `queue.resume {}` for a held queue. Send-now follows T3 queue eligibility per row (`QueuedMessage.canSendNow`), not the composer's steer gate: idle means the thread is not archived or deleted; with an active run, `canPromoteToSteer` (compaction does not block it) and the queued run is not `freshContext` unless the active turn is `/compact` (the server skips it instead). Queue state clears on thread switch and connection loss and is republished from the next selected-thread snapshot. Follow-up, queue and stop commands capture the selected thread when built and send only while the same thread is still selected and writable; a local abort before transmission is a normal error that leaves the session connected. Stop is offered while the selected thread has an active run, pending background work or an active subagent. With `environment.capabilities.threadStop` it sends `thread.stop {}` (the server stops the live run or the run behind pending background work, holding the queue, and the delegated tasks); otherwise `run.interrupt {runId, holdQueue: true}` on the last preparing/starting/running/waiting run, else on the run pending non-pull-request background work hangs off; with no such run, each active stoppable subagent is stopped as in [Subagents](#subagents) and each pull request watch (a visible link with a `watch`, merged links included) gets `thread.pull-request.watch {host, repository, number, watching: false}`, each once. Before each command of a multi-command stop the client waits briefly for a fresh projection and re-checks selection and writability; a change ends the stop. A child thread shared by several tasks is stopped once per stop. Nothing stoppable fails locally. The older single-run interrupt still sends `run.interrupt` with the active `runId`. Approval/user input uses `runtime-request.respond`; unknown/non-live request capabilities stay visible with response disabled. A new conversation is a local draft (project, server-provided model, runtime mode, default `approval-required`) that allocates a UUID `threadId` and `commandId` once and keeps them until the thread is known to exist. Its first message creates the thread like T3 web: `orchestration.launchThread` with the draft `commandId` and `threadId`, `creationSource: "mobile"`, `projectId`, `title` = T3 title seed of the message (whitespace-collapsed, at most 50 code points plus `...`, fallback `New thread`), `generateTitle: true`, `modelSelection {instanceId, model}`, the draft `runtimeMode` (refused locally when the model's provider lists `supportedRuntimeModes` without it), interaction `default`, workspace `{type: "root"}` and `initialMessage {messageId, text, attachments: []}` where `messageId` is the name-based UUID of `"<commandId>:initial-message"`, so a resend is stable. The result `{threadId, projection, resumed, sequence?}` is validated (`threadId` and `projection.thread.id` equal the draft `threadId`; otherwise uncertain) and its projection seeds the thread before it is selected. After an uncertain or rejected launch the draft and its ids stay (also across reconnect and pause/resume of the same environment); once the session is connected and the shell lists the draft `threadId`, the draft is cleared and that thread opened. Only an explicit user resend repeats `launchThread`, with the same ids: the server deduplicates by `commandId` (`resumed: true`, original title/mode/model kept; a different `threadId` under a used `commandId` is a conflict), and a launch rejected before creation (e.g. missing project) may be resent with its ids. Verified against an isolated T3 by `scripts/validate-t3-wire.mjs`. Selected-thread settings use `thread.runtime-mode.set {runtimeMode}` and `thread.model-selection.set {modelSelection {instanceId, model, options?}}`: the model must be in the server catalog; the thread's current `options` (e.g. reasoning effort) are sent only when instance and model are unchanged. A thread whose provider cannot hand off (T3 `threadSupportsProviderHandoff`: an attached session's `capabilities.sessions.supportsProviderSwitchingViaHandoff`, else an active run locks, a never-run or `v1_import` thread is free, and a finished one is free only while its native provider thread exists) refuses a change to another provider instance locally; the client exposes this as `selectedProviderLocked`. Current values are read from `projection.thread.runtimeMode` and `projection.thread.modelSelection`, the latter mapped to the matching catalog model. The first config's `settings.defaultRuntimeMode` (default `full-access`) and each provider's `supportedRuntimeModes` (provider-level, forward compatible: unknown literals skipped; absent means unrestricted) are parsed into `ClientState.defaultRuntimeMode` and `ModelOption.supportedRuntimeModes`. New-thread defaults follow T3 `resolveProjectSettings`: `settings.defaultModelSelection` (`{instanceId, model, options?}`) and each `settings.projectSettingsOverrides[projectId]` entry's `defaultModelSelection`/`defaultRuntimeMode` (the server folds legacy project-row defaults into it) become `ClientState.defaultModelSelection` and `projectDefaults`; the project override wins, a selection the catalog does not offer is skipped (next scope, then the catalog's first model), and the default's options the model still offers (e.g. reasoning effort) seed the draft until the user picks another model or effort. Usage-limit fallback (`fallbackModelSelection`) is not applied. The new-thread project picker lists projects by newest thread activity (latest user message, else updated/created; T3 sidebar `updated_at`), preselects the most recent one, and searches title and workspace path. Each catalog model's `capabilities.optionDescriptors` (`select` with choices, `currentValue`, `promptInjectedValues`, `role`; `boolean`; unknown types skipped, null capabilities = none) become `ModelOption.descriptors`; the reasoning control is the first select with `role: "reasoning"` or a known effort id, Fast mode the boolean `fastMode`. `modelSelection.options` is read in both wire forms (canonical `[{id, value}]`, legacy `{id: value}`) and written canonical: an option change (`setModelOption`) re-sends the same instance and model with the thread's other options the catalog still offers kept and that id replaced; model-selection changes run one at a time and build on the newest selection T3 accepted but the projection does not show yet (dropped once the projection shows it or another selection, and on rejection, thread switch or disconnect; never resent), a draft's options ride on `launchThread` `modelSelection.options` (only values the catalog still offers; a draft model change drops the rest), and a value the descriptor does not offer (including `promptInjectedValues`) is refused locally (never sent). The current value is the explicit option, else `currentValue`, else the `isDefault` choice (booleans: unknown); a thread selection without an explicit `variant` has no current variant.
9. Every request has a timeout; pending RPC count is bounded at 64. A lost/timeout/uncertain mutation disables writes until reconnect; a definite rejection does not. No mutation replay occurs. The next authoritative snapshot reconciles visible state; there is no automatic receipt retry.

## Current limits

The client requests complete shell history (`omitIdleSubagents: false` and `omitOlderSettled: false`), so `getOlderSettledThreads` is not needed for this full-snapshot path. Long threads show the latest 10 user turns with a client-side "Load earlier turns" control (10 more per tap) over the already loaded projection; server bounded-history paging is not used. Domain event resnapshotting trades bandwidth for completeness; native incremental reducers can replace this later. Provider approval option restrictions are checked at dispatch; the shared UI currently exposes basic accept/decline. Unsupported requests explicitly direct users to another T3 client. Auto reconnect/backoff, access-token renewal, command receipt lookup, queue reordering/editing, attachment uploads and terminal streams are follow-up work. Explicit reconnect and [file downloads](FILES.md) are implemented.

Connected-environment [usage summaries and provider limits](USAGE.md) use read-only RPCs with scoped access, caching and refresh throttling.

Side chats (`thread.fork` with `sideChat`), the read-only thread inspector and thread context references are described in [side chats](SIDE_CHATS.md).

Fixtures are synthetic examples shaped from the pinned contracts and contain no user data. The isolated server wire probe lives in `scripts/validate-t3-wire.mjs` and never touches a developer's T3 state.

## Subagents

The selected thread projection's `subagents[]` (`OrchestrationV2Subagent`) is parsed into client state on every projection refetch, which covers `subagent.updated` events. The Agents sheet lists this turn's agents; opening a row selects the child thread. Provider-native children (`creationSource: "provider"`) are read-only.

Stop is offered only while writable, for app-owned agents and Claude-native agents with a strong native ref. Each command is sent once and never replayed. Provider-native and app-owned agents send `subagent.stop {runId, subagentId}` on the parent. For an app-owned agent, the child is then stopped with `thread.stop` only when the server advertises `environment.capabilities.threadStop`; otherwise the child gets T3's run-less fallback: `run.interrupt {runId, holdQueue: true}` on its active run, else on the run its pending background work hangs off, else its pull request watches are unwatched; work that remains with nothing to stop it (for example a nested agent this client cannot stop) is reported as a partial failure. Older servers may reject `subagent.stop`; after that definite rejection the child is still stopped.

## Prompt suggestions

`orchestration.subscribePromptSuggestion` `{threadId}` streams `null` or `{runId, text}` (`OrchestrationV2PromptSuggestion`, unpersisted): the provider's predicted next message for the run that produced it. The method and the server setting `promptSuggestionsEnabled` are newer than this pin and optional. Only a JSON `true` in the first config or later `subscribeServerConfig` settings (snapshot or `settingsUpdated`) enables it; older servers omit the setting, so `true` also proves the method exists. The client subscribes the selected thread only, after that thread's own subscription is live and while the setting stays true; it interrupts the stream on thread switch, deselect, disconnect and when the setting turns false or the `subscribeServerConfig` stream ends (the setting then counts as off). The suggestion is never part of retained or cached state. A malformed item counts as `null`; the stream's end or rejection clears the suggestion, never fails the session and is not retried for that thread. The composer offers it only while its run is the thread's latest completed run (T3 `offeredPromptSuggestion` over the shell row's `latestRunId`, `latestRunStartedAt` and `status`, skipping a run cancelled before it started once the detail shows it), never auto-sends it, and the text is never logged or stored.

## Diffs and pull requests

Turn diffs come from the selected thread projection's `checkpoints` (T3 `7deb51b550`): a checkpoint is shown only with a non-null `appRunOrdinal`, which is its turn count. Turn 1 reads `orchestration.getFullThreadDiff {threadId, toTurnCount: 1}`; turn n reads `orchestration.getTurnDiff {threadId, fromTurnCount: n-1, toTurnCount: n, ignoreWhitespace: false}`. Both are reads under `orchestration:read`, guarded like other selected-thread reads, parsed off the main thread, capped at 60 000 rows, and cached in memory per environment only. An oversized reply fails only that request.

Pull request reads (`pullRequests.detail`, `pullRequests.checks`, `pullRequests.subscribeRefreshes`, `POST /api/pull-requests/diff`) are used only when `environment.capabilities.pullRequests` (and `pullRequestChecks` for checks) is `true`. A `PullRequestRef` is the thread link's `host`, `repository` and `number` plus the thread's `projectId`. The panel paints the link `snapshot`, then the server's last-good `detail`, and revalidates on refresh ticks. Caches are memory-only, per environment, and dropped when the environment is forgotten.

Pull request mutations (`pullRequests.runAction` for merge, update-branch, ready and draft; `pullRequests.comment`) need `source-control:write`, a live writable session and the action in the PR's reported capabilities. They carry no `commandId` and are not idempotent, so each is sent once and never retried or replayed; merge sends `expectedHeadSha` from the last detail. A typed `Fail` (`PullRequestUnavailableError`, `PullRequestOperationError`) is a definite rejection. A timeout, disconnect, oversized reply or Interrupt-only Exit is an uncertain outcome. Because these act on the code host and not on T3 orchestration state, an uncertain outcome is scoped to that pull request rather than failing the session (unlike item 8): the panel shows "Outcome unknown – checking…", keeps that PR's actions disabled, and reconciles with `pullRequests.detail {allowStale: false}` and `checks` on the next live session. Only the user can send the action again.

## SSH transport (0.2.0 source)

SSH is a transport wrapper around the same V2 HTTP/Effect RPC protocol. Native
SSHJ verifies the host key before password/private-key authentication. First use
requires a user-confirmed SHA-256 pin; a changed pin blocks authentication.

Read the selected T3 home's `userdata/server-runtime.json`, verify live PID and
runtime metadata, and forward an ephemeral **127.0.0.1** listener only to the
remote **127.0.0.1** T3 port. Probe the descriptor and require V2, matching
server/CLI version and the expected saved environment identity. The running
server's matching CLI executes `auth pairing create --base-dir <home> --json`;
its `credential` is exchanged through the tunnel using the existing OAuth flow.
Never log raw command output or replay pairing creation after an unknown result.
No installation, update, service change or remote process stop occurs.

SSH profiles, host pins, access tokens and explicitly saved login secrets live
in Android Keystore-encrypted local files. The local forwarded URL is transient:
it is never persisted as an environment's durable endpoint. Reconnect opens a
new SSH tunnel before reusing the saved T3 token. Background/disconnect closes
the local tunnel; remote agents continue running. An unsaved login is requested
again when a new SSH connection is needed.

## Connection setup corrections (0.2.1 source)

A transient attempt state reports testing stages, host-trust pauses, safe failures and success to retained forms. Entered secrets stay in memory only, never Android saved state. Forms close only after success or cancellation. Public-key content is rejected before SSH, hostname/username edges are trimmed, and errors scroll into view. SSH command errors may report a numeric exit code, but raw stdout/stderr is not shown because it can contain credentials.

Android cleartext configuration permits dynamic private-IP requests; the shared URL policy is the enforcement point, checking literal RFC1918 addresses and stored consent before requests. Redirects remain disabled. Both pairing and reconnect honor the consent flag; old saved environments default to false. Connection cancellation cleans the matching socket generation, and internal timeouts become actionable failures.

## Agent activity notifications

Local agent alerts are client-only. They add no fields and no RPCs. Each phase is derived only from shell snapshot rows already sent by `orchestration.subscribeShell`: the thread's own row and the rows of its subagent descendants (reached through subagents and side chats). The rules follow T3 Code `packages/shared/src/agentAwareness.ts` (`projectThreadAwarenessV2`) and the snooze check in `apps/server/src/relay/AgentAwarenessRelay.ts`.

A thread that is not listed lineage, is archived or is deleted has no phase. Otherwise the first matching rule gives its phase:

1. Its pending request is `user_input`: WaitingForInput.
2. Its pending request is another kind, not `auth_refresh`: WaitingForApproval.
3. A waiting subagent: WaitingForInput when the child's request is `user_input`, otherwise WaitingForApproval. Among several, the child with the newest `updatedAt` decides.
4. Otherwise `activityRunStatus`, or `status` when absent: `preparing` or `starting` gives Starting; `running` or `waiting` gives Running; `completed` gives Running while background work holds completion or a monitor holds wake completion, otherwise Completed; `failed` gives Failed; any other value gives no phase.

No alert is raised when:

- the phase is Completed and `latestRunStopRequested` is true;
- `settledOverride` is `settled`, the phase is Completed or Failed (or Running on a completed run), and background work does not hold completion;
- the phase is Completed and the thread was snoozed over that completion.

Alerts depend on transitions between snapshots. A transition into an attention phase (approval or input) alerts once. While a thread is already waiting, a new request id or a change between approval and input alerts again. A request that already alerted and is still pending (the thread's own or a subagent's) does not alert again when it decides the phase once more, for example after a newer subagent request was answered, unless the posted alert is of the other kind. A transition into Failed alerts at once, and a transition into Completed alerts after 5 seconds if the same completion (`latestRunId`, `latestRunCompletedAt`) still holds. A completion settled inside those 5 seconds still alerts, once, and that alert is not tracked for later cancellation. Both terminal alerts need the thread to have started or run since its last alert, or its latest run to have changed since the previous snapshot (a new `latestRunId`, or a newer `latestRunCompletedAt`), which covers a run that started and ended between two shell updates; they are skipped when `latestRunCompletedAt` is more than 2 minutes old. A finished or failed alert belongs to the run (`latestRunId`, `latestRunCompletedAt`) it was raised for: another run's completion removes it. The first snapshot after connecting sets the baseline silently, and threads already Starting or Running then count as having worked; threads already terminal then never alert for that run. A completion first held while the app is in the foreground, or with the setting off, never posts, even if the app goes to the background before it is due. A terminal alert is posted only if the live shell is still synchronized and still shows the run the rules evaluated. A connection loss on the same environment forgets the baseline but keeps posted alerts until the next fresh shell snapshot shows whether they still apply; an environment change clears them. "Fresh" means the shell stream is synchronized, independent of the selected thread's detail subscription.
